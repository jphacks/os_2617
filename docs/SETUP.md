# みんなで店決め：セットアップ・公開手順

グループで食事に行くお店を、アンケートで決める Web アプリです。
ホストが条件を決めてルームを作り、共有リンクから参加者がジャンルの好みをカードのスワイプで答えると、おすすめのお店を 1〜5 位で表示します。
店舗データは **ホットペッパー グルメサーチAPI** の実在のお店です（APIキーが未設定のときは大阪・京都の架空のサンプル 125 件で動きます）。

- **ホストが決める**: 場所（駅名・地名を自由に入力）・人数・日時・予算（下限〜上限、500円刻み）・ジャンル（ご飯／居酒屋／カフェ）
  - 評価する小カテゴリ: 既定から × で削除、自由入力で追加（そのルームだけの設定）
  - 詳細設定（開閉式）: 飲み放題・席の希望（個室／座敷・掘りごたつ）・禁煙/喫煙・テイクアウト
- **参加者が答える**: 小カテゴリを1枚ずつ、項目名と食べ物の画像のカードで評価 → 最後に一覧で確認・修正して送信
  - 右スワイプ／〇ボタン＝好き（+1）、上下スワイプ／ーボタン＝どちらでもない（0）、左スワイプ／×ボタン＝好みじゃない（−2）
  - パソコンではキーボードでも答えられます（→ 好き／↑↓ どちらでもない／← 好みじゃない／Backspace 1つ戻る）
- **結果**: 各お店に「Googleマップ」「ホットペッパー」へのリンク
- **共有**: ホスト画面と結果画面に「Blueskyで共有」ボタン（本文入りの投稿画面を開くだけ。認証不要）

| ジャンル | 小カテゴリ（既定） |
|---|---|
| ご飯 | 和食・洋食・中華・焼肉・ラーメン・うどんそば・ファストフード・粉もの・カレー・韓国料理・エスニック |
| 居酒屋 | 大衆居酒屋・焼き鳥・串揚げ・焼肉・海鮮・ワインダイニング・韓国系・バー |
| カフェ | カフェ・喫茶店・パフェ・ベーカリー・韓国系・ランチ・作業向け |

## 公開手順（Neon → Render）

コードはこのリポジトリ（`jphacks/os_2617`）の `main` ブランチにあります。

### 1. Neon でデータベースを作る（無料・カード登録不要）

1. https://neon.com でサインアップ
2. 「Create project」：名前は `mise-kime`、**Region は「AWS Asia Pacific (Singapore)」**
3. 作成後の画面の「Connect」から接続文字列（`postgresql://...neon.tech/neondb?sslmode=require...`）をコピー

テーブルはアプリの起動時に自動で作られるので、Neon 側での作業はこれだけです。

### 2. Render で公開する

1. Render のダッシュボードで「New」→「Blueprint」
2. GitHub の `jphacks/os_2617` リポジトリを選ぶ
   - 一覧に出ないときは、Render の GitHub 連携の設定で `jphacks` 組織へのアクセスを追加する（組織の管理者の承認が必要な場合があります）
3. `render.yaml` の内容が表示されるので、`DATABASE_URL` に手順 1 でコピーした接続文字列を貼り付けて「Apply」（または「Deploy Blueprint」）
4. 数分でビルドが終わると `https://mise-kime-xxxx.onrender.com` のような URL で公開されます

確認: `https://（公開URL）/healthz` を開いて `"store":"postgres"` と出ればデータベースにつながっています（`memory` と出たら `DATABASE_URL` が設定されていません）。

### 3. ホットペッパーのAPIキーを設定する（実在のお店を出す）

1. https://webservice.recruit.co.jp/register を開き、メールアドレスを登録する（無料）
2. 届いたメールの案内に沿って登録を終えると、**APIキー**（英数字の文字列）が発行されます
3. Render のダッシュボードでこのサービスを開き、左の「Environment」→「Add Environment Variable」
   - Key: `HOTPEPPER_API_KEY`
   - Value: 発行されたAPIキー
4. 「Save Changes」（「Save, rebuild, and deploy」を選べる場合はそれ）で保存して再デプロイ
5. 確認: `https://（公開URL）/healthz` に `"shops":"hotpepper"` と出れば設定できています（`"sample"` ならキーが入っていません）。
   Render の「Logs」に `[hotpepper] ジャンルマスタOK（17件）` と出ていれば、キーが正しく使えています

APIキーはサーバーの中だけで使い、画面（ブラウザ）には出しません。キーをチャットや GitHub に書かないでください。

### 公開後の修正

GitHub の `main` ブランチに push したあと、Render の「Manual Deploy」→「Deploy latest commit」で反映します（Blueprint で作った場合は push だけで自動反映）。
うまく動かなかったときは、Render の「Events」から前のデプロイに戻せます（Rollback）。

## 無料プランでの注意

- **Render（無料）**: 15 分アクセスがないと停止し、次のアクセス時に起動まで 1 分ほどかかります。毎月 750 時間まで。
- **Neon（無料）**: 5 分使われないと停止し、次のアクセス時に数秒で再開します。容量は 1 プロジェクトあたり 1GB で、このアプリの用途なら十分です。
- データは Neon に保存されるので、Render が停止・再デプロイしてもルームと回答は消えません。

## 設定（Render の「Environment」で変更）

| 変数 | 内容 |
|---|---|
| `DATABASE_URL` | Neon の接続文字列。未設定だとメモリ保存（再起動で消える） |
| `HOTPEPPER_API_KEY` | ホットペッパーのAPIキー。未設定だと架空のサンプル店舗（大阪・京都）で動く |
| `DEMO_TOOLS` | `false` にするとホスト画面の「サンプル回答を1件追加」ボタンを隠す |

## 手元で動かす

Node.js 22 が必要です。

```bash
npm install
npm start          # http://localhost:3000 （DATABASE_URL がなければメモリ保存、HOTPEPPER_API_KEY がなければサンプル店舗）
npm test           # 読み取り・ジャンル判定の単体テストと、API の一連の流れを自動チェック（通信は偽の応答で代用）
npm run demo       # ランキングの計算だけを試す（例：npm run demo -- 渋谷）
```

## API

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/options` | 選択肢（予算・ジャンル・評価など）と、お店のデータ元（`hotpepper` / `sample`） |
| POST | `/api/rooms` | ルーム作成 `{ location, people, datetime, budgetMin, budgetMax, category, subs, nomihodai, seat, smoking, takeout }`。`location` は地名（ホットペッパーのキーワード検索で座標にする）。`subs` は `[{ value: "yakitori" }, { label: "もつ鍋", custom: true }]`（省略時は既定のすべて）。予算は 500 円刻み、`null` は指定なし。詳細設定は省略可 |
| GET | `/api/rooms/:id` | ルーム情報と回答状況 |
| POST | `/api/rooms/:id/answers` | 回答 `{ name, ratings: { 小カテゴリ: "great" \| "ok" \| "ng" } }`。同じ名前は上書き。人数に達したら自動締め切り |
| POST | `/api/rooms/:id/close` | 締め切り `{ hostToken }` |
| POST | `/api/rooms/:id/sample-answer` | 動作確認用のサンプル回答 `{ hostToken }` |
| GET | `/api/rooms/:id/result` | ランキング（受付中は `{ pending: true, room }`） |
| GET | `/healthz` | 死活確認 |

## お店の取得（`src/shopSource.js`・`src/hotpepper.js`）

1. **場所 → 座標**: 入力された地名でホットペッパーの「キーワード」検索（店名・住所・駅名などの部分一致）を行い、
   ヒットしたお店（最大100件）の座標の中央値を中心にします。中央値から 3km 以上離れたお店（同じ名前の別の街など）は外して平均を取り直します。
2. **候補の取得**: 中心から半径 1km → 足りなければ 2km → 3km と広げて、ジャンルの対象のお店を最大 200 件取得。
   さらに小カテゴリごとのキーワード（焼き鳥・パフェ・ホストが追加した「もつ鍋」など）でも検索して取りこぼしを防ぎます。
3. **変換**: ホットペッパーの文章の項目を数値などに読み替えます（`src/shopData.js`）。読み取れない項目は「不明」とし、除外も減点もしません。

   | ホットペッパーの項目 | 使い方 |
   |---|---|
   | `budget.average`（平均予算） | 「ディナー3000円 ランチ1000円」などから金額を読む。なければ予算コード（例：B003 = 3001〜4000円）の中央値 |
   | `open` / `close`（営業時間・定休日） | 曜日ごとの営業時間・定休日に読み替えて、営業時間外・定休日のお店を除外 |
   | `capacity` / `party_capacity` | 人数オーバーの判定 |
   | `non_smoking` | 全面禁煙 / 一部禁煙（分煙）/ 禁煙席なし（喫煙可） |
   | `private_room` / `tatami`・`horigotatsu` / `free_drink` | 個室 / 座敷・掘りごたつ / 飲み放題 の あり・なし |
   | 店名・キャッチ・備考の文章 | 小カテゴリの判定、テイクアウトの推定（「テイクアウト」「持ち帰り」の記載） |

ホットペッパーの利用規約に合わせて、検索結果のキャッシュは 1 時間（規約は 24 時間以内）で、店舗情報はデータベースに保存しません。
結果画面にはクレジット（Powered by ホットペッパーグルメ Webサービス）を表示しています。

### ジャンルの対応表（`src/genreMap.js`）

## ランキングの考え方（`src/ranking.js`）

1. **足切り**: ジャンル外（どの小カテゴリにも当たらない・削除された小カテゴリ）・中心から 3.5km 超・定休日・営業時間外・人数オーバーのお店を除外。
   禁煙希望なら「喫煙可」の店、喫煙可希望なら「全面禁煙」の店も除外（分煙・不明の店はどちらでも残す）
2. **採点**: 項目ごとに 0〜1 で採点し、重み付き平均で 100 点満点にする。お店の情報がない項目は 0.5 点

   | 項目 | 重み | 採点 |
   |---|---|---|
   | 場所 | 30 | 中心からの距離で減衰（1.5km で約 0.37） |
   | 予算 | 25 | 下限〜上限に入っていれば満点。上振れに厳しく減点（指定なしなら採点しない） |
   | 小カテゴリ | 25 | そのお店の小カテゴリへの 〇ー× の 1 人あたり平均を、全員〇=1・全員ー=0.5・全員×=0 に換算 |
   | 飲み放題 | 10 | ホストが「必須」のときだけ。なければさらに ×0.6 |
   | 席 | 10 | ホストが個室・座敷を希望したときだけ。あれば満点 |
   | テイクアウト | 加点 | ホストが「希望する」とき、紹介文に記載のあるお店に +5 点（ホットペッパーに項目がないため、記載のないお店は減点しない） |

3. **並べ替え**: 点数 → 距離 の順で上位 5 件

**〇ー× の配点について**: 順位を決めるのは配点の比だけで、今は「×1つが〇2つ分を打ち消す」設定です。
シミュレーションで、全体の満足度と「不満な人を出さないこと」のバランスが最も良かった比です。
重み 25 と合わせて、全員が〇を付けた小カテゴリなら、約 1.2km 遠いお店でも逆転できる強さにしています。

重みやしきい値は `src/ranking.js` 冒頭の定数で調整できます。

## アンケートのカードの画像

画像は `public/food/` に置き、`src/foodImages.js` に「小カテゴリ名: ファイル名」を書くと、アンケートのカードに表示されます
（例：`'海鮮': 'kaisen.webp'`）。名前で対応づけるので、ホストが追加した小カテゴリも名前が一致すれば画像が出ます。
画像のない小カテゴリは、名前を大きく書いた文字だけのカードになります。
